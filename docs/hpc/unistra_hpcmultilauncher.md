# How Unistra's `hpc_multilauncher` runs a study

This document explains the launcher supplied in the Unistra workflow and the
scratch-mode jobfile generated by WormWeaver. The example jobfile has 60 lines,
ordered `sim1` through `sim60`, with one complete simulation command per line.
For installation and study generation, see [the Unistra HPC guide](../unistra-hpc.md).

There are two levels of parallelism:

1. Slurm allocates a node to each array task and runs the batch script there.
2. Each task selects a fixed chunk of the jobfile and uses GNU Parallel to run
   commands from that chunk on its node.

## Submit the batch script as an array

The supplied account script is:

```bash
#!/bin/bash
#SBATCH -N 1 --exclusive
#SBATCH --mem-per-cpu=4000
#SBATCH -p grant -A g2026a136c
#SBATCH -t 4-00:00:00

module load gcc/15.2.0

commandes=jobfile
hpc_multilauncher $commandes
```

It requests one exclusive node per array task. It does not specify the array
itself. Submit from the study directory with, for example:

```bash
sbatch --array=1-3 grant_g2026a136c.slurm
```

Alternatively, add `#SBATCH --array=1-3` among the script's Slurm directives.
Without an array submission, the launcher's check for `SLURM_ARRAY_TASK_MAX`
prints a submission hint and exits before running simulations.

Each array task receives its own environment, including:

| Variable | Meaning |
| --- | --- |
| `SLURM_ARRAY_JOB_ID` | Base ID identifying the whole array |
| `SLURM_ARRAY_TASK_ID` | Index identifying this task within the array |
| `SLURM_ARRAY_TASK_MAX` | Highest configured array index |
| `SLURM_JOB_ID` | Numeric job ID identifying this task's allocation |
| `SLURM_CPUS_ON_NODE` | Allocated CPU count on the current node |

The numeric job ID cannot be calculated from the task index. Query Slurm for
the mapping. See [Slurm's array documentation](https://slurm.schedmd.com/job_array.html).

## Divide the jobfile into fixed chunks

The launcher reads the jobfile path from its first argument and checks that the
file exists. It then calculates:

```text
L = number of lines in the jobfile, counted by wc -l
M = SLURM_ARRAY_TASK_MAX
i = SLURM_ARRAY_TASK_ID
q = floor(L / M)

first line = 1 + (i - 1) * q
last line  = i * q              when i < M
last line  = L                  when i = M
```

For 60 commands submitted with `--array=1-3`, `q = 20`:

| Array index | Selected jobfile lines | Assigned simulations |
| --- | --- | --- |
| `1` | 1–20 | `sim1`–`sim20` |
| `2` | 21–40 | `sim21`–`sim40` |
| `3` | 41–60 | `sim41`–`sim60` |

The final task gets any remainder. For example, 62 commands divided among the
same three indices give 20, 20, and 22 commands respectively.

This is static assignment. A task that finishes its chunk early does not take
commands from another task. Simulations map to chunks by jobfile line order;
the `simN` ranges above depend on the example file being ordered by simulation
number.

The launcher extracts the selected lines into a temporary file:

```bash
sed -n "${ligneDebut},${ligneFin}p" $commandes \
    > $commandes.$SLURM_ARRAY_JOB_ID.$SLURM_ARRAY_TASK_ID
```

For task `18523211_2`, the file is `jobfile.18523211.2`. This filename uses the
array ID and index, whereas the scratch directory uses `SLURM_JOB_ID`.

## Run each chunk with GNU Parallel

The optional second launcher argument describes the CPU threads budgeted per
command. With the batch script above, it defaults to one:

```bash
threads=${2-1}
num_procs=$SLURM_CPUS_ON_NODE/$threads

parallel -j $num_procs \
    -a $commandes.$SLURM_ARRAY_JOB_ID.$SLURM_ARRAY_TASK_ID
```

The integer `num_procs` is the maximum number of simultaneous command slots.
Each command slot executes one complete jobfile line, including its copies
and Julia invocation.

For a chunk containing 20 commands:

| Allocated CPUs | Threads argument | Command slots | Behavior |
| --- | --- | --- | --- |
| 40 | 1 | 40 | All 20 commands can run concurrently |
| 8 | 1 | 8 | Up to 8 run; another starts as a slot becomes available |
| 40 | 4 | 10 | Up to 10 run concurrently |

For the last example, the batch script would call `hpc_multilauncher jobfile 4`.
This argument only reduces concurrency. It does not set Julia or BLAS thread
counts or bind individual simulations to specific CPUs. Configure the
simulation's threading separately and budget slots accordingly.

There is no remote-host configuration or `srun` in this GNU Parallel command.
It runs commands locally on the node executing the batch script. Although the
launcher's comments mention multiple nodes, the shown implementation does not
distribute commands across additional nodes if the allocation is enlarged.

## Follow one simulation through scratch and copy-back

Each scratch-mode jobfile line has this sequence, using `sim21` as an example:

```bash
cp -r /path/to/study/sim21 /scratch/job.$SLURM_JOB_ID/sim21;
cd /scratch/job.$SLURM_JOB_ID/sim21;
julia /path/to/multiwormqmc.jl/bin/multiwormqmc.jl config.yaml &> simulation.log;
cp -r /scratch/job.$SLURM_JOB_ID/sim21/* /path/to/study/sim21;
```

These commands occupy a single line in the actual jobfile. The shell expands
`SLURM_JOB_ID` when the command runs on the compute node.

1. Copy the simulation folder from the study filesystem into node-local scratch.
2. Change into that scratch simulation directory.
3. Run Julia, redirecting stdout and stderr into the scratch `simulation.log`.
4. After Julia exits, copy non-hidden contents back into the study folder.

The `/scratch/job.<jobid>` parent directory must already exist. Relative output
filenames in the simulation config resolve inside the scratch simulation
directory. Absolute output paths continue to refer to their configured
locations.

Copy-back happens independently after each simulation exits. A finished
simulation can therefore have its log and results back in the study directory
while other simulations in the same array task are still running. The original
study log is not continuously updated during scratch execution.

GNU Parallel waits for all commands in the chunk to finish. The launcher then
removes its temporary `jobfile.<arrayid>.<index>` file and exits.

## Locate simulations for monitoring

From the login node, query the mapping between array tasks, numeric job IDs,
states, and allocated nodes:

```bash
squeue -h -r -j 18523211 -o '%i|%A|%T|%N'
```

The following mapping was reported during inspection; it is an example rather
than a live status report:

```text
18523211_3|18523211|RUNNING|hpc-n937
18523211_2|18523213|RUNNING|hpc-n664
```

If that array executes the 60-line example with original indices `1-3`, its
scratch locations are:

| Array task | Numeric job ID | Node | Assigned scratch simulation directories |
| --- | --- | --- | --- |
| `18523211_2` | `18523213` | `hpc-n664` | `/scratch/job.18523213/sim21` through `sim40` |
| `18523211_3` | `18523211` | `hpc-n937` | `/scratch/job.18523211/sim41` through `sim60` |

WormWeaver exposes the allocation lookup through:

```julia
using WormWeaver

tasks = slurm_array_tasks(18523211)
# A task ID also queries its siblings:
tasks = slurm_array_tasks("18523211_2")
```

The function reports the expected scratch parent directory for each task. It
does not inspect scratch, verify directories, determine simulation assignment,
or read simulation logs. It includes only tasks currently returned by `squeue`;
completed tasks may be absent and pending tasks may lack assigned nodes.

To locate existing scratch logs for simulations listed in the study manifest:

```julia
logs = find_scratch_logs(study_dir, 18523211)
# Optional custom scratch root; a task ID also inspects the whole array:
logs = find_scratch_logs(study_dir, "18523211_2"; scratch_root="/scratch")
```

This returns `simulation`, `task`, `jobid`, `node`, and `log_path` in manifest
simulation order, retaining multiple locations for the same simulation. It
reads only `manifest.jld2`; `manifest.csv` is not a fallback. It
checks running allocations with one `srun` per allocation and node; missing
logs are omitted and inspection failures raise errors. It only locates files:
log contents and simulation status are not read. Existing launcher and copying
behavior remain unchanged.

Read one discovered log into a Julia string with:

```julia
text = read_scratch_log(logs[1, :])
```

This reads the entire log through `srun` using the selected row's job ID, node,
and path. It preserves the text, does not copy or modify files, and does not
parse simulation status. An ended allocation or an unreadable/missing log
raises an error; discovery and reading happen at different times.

Parse the log text with the public status parser:

```julia
progress = study_log_status(IOBuffer(text))
```

This applies the same stage, checkpoint, failure, and completion rules as local
log parsing. The file-path method continues to work as before.

To obtain one status row per manifest simulation, including scratch logs:

```julia
statuses = study_status(study_dir; arrayid=18523211, scratch_root="/scratch")
```

A unique scratch log takes precedence; simulations without one use their
study-directory log. `log_source` records `"scratch"`, `"local"`, or `"none"`
when no log exists. Multiple scratch matches and read failures raise errors.
An empty but existing log is still recorded as `"scratch"` or `"local"`.
`study_status(study_dir)` reads only local logs and also includes `log_source`.
This does not change how simulations run or copy files. To retain all manifest
parameters along with refreshed progress and `log_source`, use:

```julia
snapshot = status_manifest(study_dir; arrayid=18523211, scratch_root="/scratch")
# Save the same information in a new timestamped JLD2 snapshot:
snapshot = status_manifest(study_dir; arrayid=18523211, save=true)
```

Without `arrayid`, snapshots read only study-directory logs. All collection
functions use the JLD2 manifest; source manifests and simulation files stay
unchanged. An already-loaded manifest is reused during scratch discovery.

### Terminal dashboard

```julia
status_summary(statuses);                  # Full dashboard, without REPL table echo.
status_summary(statuses; detailed=false);  # Overall and parameter summaries.
counts = status_summary_data(statuses)     # Pure calculation; no terminal output.
```

The dashboard shows overall counts and percentages, a parameter table only
when multiple lattice/beta combinations exist, and detailed stage counts by
source. For a single combination, full lattice dimensions and beta appear
once in the header. Stage rows combine Local and Scratch counts; a No log
column appears for missing logs and an Unspecified column accounts for unknown
source labels. Older tables without `log_source` show stage totals only.
Failed rows retain their last stage, such as `Failed (Tuning)`.

`counts` contains the original grouped `summary`, `overall`, `parameters`,
`stages`, and `has_source`. The dashboard retains the same grouped return table
as before; rendering order and combined source columns affect only the display.
Failures take precedence over success markers in the summary counts.

Dark2_8 green marks successful finishes, orange marks failures, and unfinished
stages remain neutral. Colors follow the IO context and are disabled for plain
output. Use `io=devnull` to suppress all printing or an IOBuffer/file to capture
it. The dashboard reports log-derived progress, not whether Slurm tasks or
individual simulation processes are currently running.

To inspect a log on the node while its allocation is still running:

```bash
srun --jobid=18523213 --nodelist=hpc-n664 --overlap \
    --nodes=1 --ntasks=1 \
    tail -n 10 /scratch/job.18523213/sim21/simulation.log
```

This launches a short read operation inside the existing allocation. Verify
that the cluster permits overlapping monitoring steps; see the
[`srun` documentation](https://slurm.schedmd.com/srun.html).

Assignment does not establish that a simulation has started: its command may
still be waiting for a GNU Parallel slot. Likewise, a running array task does
not mean every assigned simulation is running. Use the original configured
highest array index when calculating chunks, rather than the number or highest
index of tasks still visible in `squeue`. Missing logs alone do not establish
failure or completion. A tail is useful for inspection; accurate stage parsing
may require earlier log lines as well.

## Constraints of the supplied launcher

- The chunk formula assumes consecutive indices starting at `1`. Sparse arrays,
  zero-based arrays, and arrays starting at another index do not produce the
  intended complete partition. Use no more array tasks than jobfile commands.
- The launcher is labeled `#!/bin/sh` but uses Bash features such as `[[ ... ]]`,
  `declare`, and arithmetic commands. Its interpreter should be Bash. A Bash
  parent batch script does not override an executable launcher's shebang.
- Its thread validation pattern, `^[1-9]+$`, rejects positive integers containing
  zero, including `10` and `20`. The intended positive-integer pattern is
  `^[1-9][0-9]*$`. Also ensure the CPU/thread division gives at least one slot.
- The scratch commands use `;`, so a failed copy or directory change does not
  automatically stop the remaining commands. Copy-back is attempted even after
  Julia fails, and its exit status can mask Julia's failure. The launcher's final
  `rm` can also mask GNU Parallel's exit status. Check the simulation log for
  reported success or failure.
- Copy-back uses `*`, which omits hidden files. Interruption or node failure can
  leave output only on scratch; scratch availability after the allocation ends
  depends on cluster policy.

These points describe the supplied launcher and generated command format.
This document does not change their execution behavior.
